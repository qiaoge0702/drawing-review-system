# M1 骨架代码审查报告

- **审查范围**：`app/generators/`（pipeline.py / models.py / steps/step1、step2）+ `app/models/generation.py` + `tests/test_generators/`
- **审查日期**：2026-07-30
- **审查人**：reviewer（子代理）
- **审查方式**：只读静态审查，未修改任何代码

---

## 【阻断级】（必须修复后才能进入 M1 收口）

### B1. 失败步骤的检查点被保存，恢复时被当作"已完成"加载
- **位置**：`app/generators/pipeline.py:133`（`_save_checkpoint(task_id, step_result)` 无条件调用）、`:101-107`（`_load_checkpoint` 不校验 status）
- **问题**：`_execute_step` 返回后无论成功失败都写 checkpoint；`run()` 中 `_has_checkpoint` 命中即 `continue`，不检查 `step_result.is_success`。后果：步骤失败后重启任务，**失败的 checkpoint 会被当作已完成加载**，流水线带着错误状态继续往下跑，中间产物缺失/错误会静默传播到 Step 7 DXF 构建。这是检查点机制的根基性缺陷。
- **建议修法**：`_save_checkpoint` 仅在 `step_result.is_success` 时写入；或 `_load_checkpoint` 后校验 `status == COMPLETED`，否则清除并重新执行。两者都做（防御式）。

### B2. asyncio.wait_for 超时对同步 COM 调用无效
- **位置**：`app/generators/steps/step1_sw_load.py:116`（`self._parser.parse_assembly(filepath)` 同步调用）、`step2_geometry_parse.py:139`（`self._parser.get_bom(filepath)`）；被调用处 `pipeline.py:222`（`asyncio.wait_for(executor(ctx), timeout=...)`）
- **问题**：SWParser 的 COM 调用是同步阻塞的，直接写在 `async def` 里会阻塞事件循环，`wait_for` 的 timeout 只有在协程挂起点才能生效——**SW 卡死时超时机制完全失效**，整个进程挂起。M1 需求明确要求"超时/重试"，此项当前不可用。
- **建议修法**：用 `asyncio.to_thread(...)`（或 run_in_executor）包裹所有同步 COM 调用，并注意 COM 套间线程亲和性（pywin32 需在初始化 COM 的线程中调用，建议专用 worker 线程 + `pythoncom.CoInitialize`）。同时为硬超时兜底（进程级看门狗）。

### B3. SW COM 资源只 close_document，从不释放 SW 应用实例
- **位置**：`step1_sw_load.py:40`（`self._parser = SWParser()`，实例长期持有）、`:91-97`（finally 仅 `close_document`）；`step2_geometry_parse.py:36-37, 106-111` 同构
- **问题**：Executor 是长生命周期对象（注册在 pipeline 上），每次执行新建 SWParser 但旧实例不释放；SW 进程（SLDWORKS.exe）只增不减，长时间运行必然句柄/内存泄漏。且步骤失败重试时又 new 一个 parser。
- **建议修法**：明确 SWParser 生命周期契约——要么 Executor 持有单一 parser 并实现 `close()/dispose()`（pipeline 在任务结束时统一调用），要么每次 `with` 式获取释放。COM 引用需显式 `Release`/置 None + `gc`，必要时 kill 残留 SLDWORKS 进程。

### B4. `_save_snapshot` 返回不存在的文件路径
- **位置**：`step1_sw_load.py:214-244`
- **问题**：截图保存是占位实现（`model_view.SaveAsImage` 被注释），但函数照样 `return str(snapshot_path)`，上游把 `snapshot_path` 写进 output_data 并持久化到 checkpoint。**下游步骤会按契约消费一个根本不存在的文件**，M2 集成时炸点隐蔽。另外 `doc = self._parser.open_document(filepath)` 的返回契约（COM 对象）未经空值/异常保护就被取 `.ActiveView`。
- **建议修法**：占位阶段返回 `None` 并记 warning，或写占位 PNG 文件保证路径真实存在；在 API 契约冻结前明确 `snapshot_path` 的语义（可选字段）。

### B5. 重试计数逻辑错误，max_retries=2 实际只重试 1 次
- **位置**：`pipeline.py:136-156`
- **问题**：重试时新建的 `StepResult(execution_count=1)`（`:189`），判断 `step_result.execution_count < step_config.max_retries` 永远用的是第一次失败的计数（1 < 2 → 重试一次）；重试再失败即 break。即"max_retries=2"语义下实际只尝试 2 次（1 原始 + 1 重试），且 `execution_count` 从未正确累加，审计日志失真。
- **建议修法**：重试循环化（`for attempt in range(max_retries + 1)`），`execution_count = attempt + 1`，并保留每次 attempt 的错误历史（`StepResult.logs` 或 attempts 列表）。

### B6. 检查点文件损坏时整个任务崩溃
- **位置**：`pipeline.py:264-269`（`_load_checkpoint` 裸 `json.load` + `StepResult(**data)`）
- **问题**：JSON 截断（进程崩溃在写文件中途）或模型字段变更（M2 演进）→ 抛异常 → 被 `run()` 外层 except 捕获 → 任务直接 ERROR，**检查点恢复机制反而降低了健壮性**。
- **建议修法**：`_load_checkpoint` 捕获 `json.JSONDecodeError` / pydantic `ValidationError`，记 warning 后视为无 checkpoint 重新执行该步；写入采用临时文件 + `os.replace` 原子落盘。

## 【建议级】

### S1. Step1 异常包装丢失原始错误码
- `step1_sw_load.py:81-90`：`except Exception` 把 `SWException(GEN_INVALID_FILE)`（文件不存在/类型不支持）也重包成 `GEN_SW_NOT_AVAILABLE`，上层无法区分"文件问题"与"SW 环境问题"，重试策略会误判（文件不存在也重试毫无意义）。
- 建议：`except SWException: raise` 放前面，仅对非预期异常包装。

### S2. Step2 BOM 提取失败静默返回空表
- `step2_geometry_parse.py:152-155`：`_extract_bom` 吞掉异常返回 `[]`，BOM 为空与提取失败不可区分，Step 5 BOM 生成将基于空数据"成功"。
- 建议：失败应抛出让步骤 ERROR；如确需降级，result 中加 `bom_extraction_failed: true` 标记。

### S3. `rerun_from` 缺参数校验
- `pipeline.py:162-185`：`from_step` 未校验 1-8 范围（传 0/9 静默行为怪异）；`parameter_overrides` 直接 `setattr(config, key, value)`，未知键 pydantic 默认行为下可能静默忽略或抛错（取决于 model_config），且绕过 validator。
- 建议：入口校验 `1 <= from_step <= 8`；overrides 用 `config.model_copy(update=...)` + 重新 validate，未知键显式报错。

### S4. 并发假设未声明
- `pipeline.py` 整体：同一 `task_id` 并发调用 `run()`/`rerun_from()` 无任何互斥，checkpoint 文件会互相踩踏；`_save_checkpoint` 非原子写。
- 建议：至少文档声明"单任务单执行者"，或加 per-task asyncio.Lock。

### S5. Step2 占位函数返回假数据
- `step2_geometry_parse.py:201-219`：`_analyze_materials` 返回空 dict、`_calculate_total_mass` 恒返回 0.0，且 `_extract_bom` 的 "GB/T" 判断大小写敏感与 `_guess_part_type`（转大写）口径不一致（`:160-162` vs `:66-67`）。`_guess_part_type` 中 `"GB" in name_upper` 过宽（会误中 "RGB"、"GBE" 等）。
- 建议：M1 可保留占位，但在 docstring/契约中标注 "placeholder, M2 实装"；标准件判断统一走 `_guess_part_type` 并用正则 `\bGB/?T?\b`。

### S6. Executor 注册机制缺校验
- `pipeline.py:73-76, 215-222`：注册时不校验类型签名；执行时才发现未注册（抛 GEN_PIPELINE_ERROR，好）但未注册步骤的错误与执行失败混在同一路径。STEP_CONFIGS 与 executor 注册的完整性无启动期自检。
- 建议：提供 `validate_executors()`（启动时检查 8 步全部注册）；注册时用 `StepExecutor` 协议做 isinstance/签名检查。

### S7. 产物收集只扫一层且不过滤
- `pipeline.py:230-241`：仅 `output_dir.iterdir()` 一层，不递归；无大小上限/类型白名单。M2 步骤产物增多后可能把临时文件也登记为 Artifact。
- 建议：约定产物清单由 executor 显式返回，iterdir 仅作兜底。

### S8. 模型字段前瞻 M2 的缺口
- `app/models/generation.py`：
  - `TaskResult.output_file` 存在但 pipeline 从不赋值（Step 7 产物未回写）。
  - 无 `parent_task_id`/`rerun_of` 字段，重跑谱系不可追溯（`rerun_from` 覆盖 result.json，历史丢失）。
  - `StepResult.logs: List[str]` 从未被写入（executor 日志只进 logging）。
  - `GenerateSettings.max_concurrent_steps` 定义了但 pipeline 完全未使用。
- 建议：契约冻结前补齐 rerun 谱系字段；明确 output_file 由谁赋值；logs 或删除或接线。

### S9. 测试覆盖缺口（关键路径未测）
- `tests/test_generators/test_pipeline.py`：
  1. **无失败 checkpoint 恢复测试** —— 正是 B1 缺陷，现有 `test_pipeline_checkpoint` 只测成功路径，漏检。
  2. **重试路径未断言次数**：`test_pipeline_step_failure` 中 Step1 retryable=True, max_retries=2，失败时会真实重试，但测试未断言 `call_count`（当前实现下为 2，修复 B5 后应为 3）。
  3. 无 `rerun_from` + `parameter_overrides` 测试；无 from_step 非法值测试。
  4. 无 checkpoint 文件损坏测试。
  5. `test_step_timeout` 依赖 MockExecutor 是 async sleep 才能被 wait_for 取消——**恰好掩盖了 B2**（真实 COM 同步调用测不出）。建议增加一个同步阻塞 executor 的用例（修复 B2 后验证）。
  6. `tests/test_generators/steps/` 目录为空，step1/step2 无任何单测（即便可 mock SWParser）。
- 另外 `test_models.py:229` `TaskConfig(drawing_type="weldment")` 传字符串靠 pydantic 强转，可过但建议用枚举。

## 【提示级】

- **T1** `pipeline.py:6` `import os` 未使用；`step1_sw_load.py:10` `SWAssembly, SWPart` 导入未使用；`models.py`（generators）`StepStatus, Artifact` 导入未使用。ruff F401。
- **T2** 全量使用 `datetime.utcnow()`（pipeline.py 多处、generation.py:52,133 等），Python 3.12 已 DeprecationWarning，建议 `datetime.now(timezone.utc)`，否则 CI 开 `-W error` 会炸。
- **T3** `pipeline.py:96` `STEP_CONFIGS[step_num - 1]` 依赖列表顺序与步骤编号强耦合，增加按 `name`/编号查找的防御（或 assert）。
- **T4** `pipeline.py:257` `_guess_artifact_type` 未知后缀默认为 JSON 会误导下游，建议新增 `OTHER` 枚举值。
- **T5** `generators/models.py:21` `StepContext.input_data` 字段定义后全程未使用，要么接线要么删除，避免契约噪音。
- **T6** mypy 风险：`pipeline.py:64` `_step_executors: Dict[StepName, Any]` 全 Any；`step1/2` 中 `self._parser.parse_assembly` 在 `self._parser` 标注为 `Optional` 时属性访问需收窄（当前靠时序保证，mypy strict 会报）。建议引入 `StepExecutor` Protocol。
- **T7** `__init__.py` 导出了 `StepResult/StepStatus/Artifact/PipelineState` 但未导出 `StepName/TaskConfig` 之外的 `DrawingType` 等，导出清单与"API 契约冻结"目标应对齐确认一次。
- **T8** `test_pipeline.py:171` 等直接调用私有方法 `_has_checkpoint/_save_task_config`，契约冻结后重构成本高，建议通过公开行为断言。

## 结论

**不建议直接进入 M1 收口。** 阻断级 6 项中 B1（失败 checkpoint 被当成功恢复）、B2（超时机制对同步 COM 无效）、B5（重试计数错误）直接命中 M1 立项要求的三项核心能力（检查点恢复、超时、重试），属于"骨架看似通、关键点断裂"的典型状态；B3/B4 关系到 SW 资源安全与契约可信度。建议修复全部阻断级 + S9 的补充测试（尤其失败恢复、重试次数断言两条用例）后复审，建议级可在收口前并行处理，提示级随 M2 顺手清理。
