## 二、新增代码审查

### 【阻断级】

### 【建议级】

**S1. artifacts 下载依赖服务端存储的 artifact.path，缺少落点校验**
`app/routers/generate.py` download_artifact（约 :140-150）：`filename` 必须与 `artifact.name` 精确相等（遍历产物清单），名义文件名不含路径分隔符，直接穿越已被间接阻断；但最终 `FileResponse(Path(artifact.path).resolve())` 服务于磁盘 result.json 中存储的任意路径——若存储目录可被写（或 checkpoint/result 被篡改），可读任意文件。
建议：增加 `file_path.is_relative_to(step_dir.resolve())` 校验，纵深防御。

**S2. task_id 未做格式校验，磁盘回退路径可目录逃逸**
`app/services/generation_service.py:121`：`GeneratePipeline().storage_root / task_id / "result.json"`，task_id 来自 URL path 段，未限制字符集（如 `..`、绝对路径片段）。影响有限（仅读名为 result.json 的文件且需通过 TaskResult 校验），但属输入校验缺口。
建议：统一校验 `task_id` 为 `^[a-f0-9]{12}$`（生成处即 uuid4().hex[:12]）。

**S3. WS 连接表单连接假设，旧连接断开会误删新连接注册**
`app/main.py:566/587`：`_websocket_connections[task_id] = websocket` 后连接覆盖先连接；先连接断开时 `finally: _websocket_connections.pop(task_id)` 会把**后连接**的注册一并删除，此后该任务进度推送静默丢失。
建议：pop 前比较对象身份（`if _websocket_connections.get(task_id) is websocket`），或改为 set。

**S4. 超时回归测试耗时约 180s**
`tests/test_generators/test_pipeline.py` `test_step_timeout`：slow_executor delay=100s，Step1 timeout=60s 且 retryable+max_retries=2 → 3 次超时共 ~180s。
建议：改用非 retryable 步骤（如 GEOMETRY_PARSE）或 monkeypatch `STEP_CONFIGS` 的 timeout 为 0.1s。

**S5.【关联风险】SWParser.quit() = ExitApp()，每步重启 SW 且可能误杀用户实例**
step1/step2 均"创建 parser → 用完 quit"；`sw_parser.py:298-302` quit 调 `ExitApp()`。后果：(a) Step1、Step2 各自完整启动/关闭一次 SW 进程，单任务至少 2 次 SW 冷启动（分钟级开销）；(b) `Dispatch('SldWorks.Application')` 可能附加到用户已打开的 SW 实例，quit 会连用户会话一起关闭。
建议：M2 将 SW 会话生命周期上移到任务级（一个任务一个 parser），并评估 `ExitApp` 前检查是否为自有实例。

**S6. step2 异常包装吞掉 SWException 原始错误码**
`step2_geometry_parse.py:112`：`except Exception` 一律包装为 `GEN_STEP_FAILED`，与 step1 的 `except SWException: raise` 处理不一致，丢失 GEN_SW_NOT_AVAILABLE/GEN_INVALID_FILE 等可判别错误码。
建议：照抄 step1 的 SWException 透传分支。

**S7. parameter_overrides 未校验，未知键/错类型在 worker 内才爆**
`pipeline.py:237`：`setattr(config, key, value)` 无 validate_assignment，未知键在 pydantic v2 下抛 ValueError——但该异常发生在 worker 执行任务时，任务直接 ERROR，而 API 层（rerun_task）只校验 from_step。契约上调用方无法预知哪些 key 合法。
建议：rerun_task 内用 `TaskConfig.model_fields` 预校验 key 白名单，非法 key 返回 400。

**S8. result.json 写入非原子 + 磁盘回退解析无容错**
`pipeline.py:422` `_save_task_result` 直接 open/write，与检查点的原子写入不一致；崩溃截断后 `generation_service.get_task` 的 `json.load`/`TaskResult(**data)` 无 try，磁盘回退直接 500。
建议：result.json 复用 tmp+os.replace；get_task 磁盘回退加容错（损坏则抛 KeyError→404 或明确 5xx 文案）。

**S9. 不可恢复错误也走满重试**
pipeline.py 重试循环不区分异常类型：step1 文件不存在（GEN_INVALID_FILE）属永久错误，仍会 retryable 步骤跑满 3 次（每次含 SW 启动开销，分钟级浪费）。SWException 已有 `recoverable` 字段（exceptions.py:214）但流水线未消费。
建议：重试循环检查 `getattr(e, "recoverable", True)`，不可恢复即 break。

### 【提示级】

- **P1** `generation_service.py:49` `self._lock` 定义后从未使用，死代码。
- **P2** 检查点命中的步骤不发任何进度事件（pipeline.py:130-137），跳步时前端只能靠 finished 一次性刷新；M1 可接受，标记。
- **P3** `ws.js` 重连无上限无退避：服务端不可达且任务状态未刷新时按 3s 固定间隔无限重连；建议指数退避 + 最大次数。
- **P4** B6 原子写入（tmp+os.replace）本身无直接测试（现有测试覆盖"损坏重跑"），可用 mock `os.replace` 抛错验证 tmp 清理路径，随 M2 补。
- **P5** `get_task` 每次磁盘回退新建 `GeneratePipeline()`（带 mkdir 副作用），建议缓存 storage_root 或提取路径工具函数。
- **P6** `step2_geometry_parse.py:99` 函数内 `import json`，挪到模块头。
- **P7** 服务重启后，重启前处于 QUEUED 的任务无 result.json、不在内存，静默丢失（磁盘恢复只覆盖已完成任务）；M1 可接受，建议 TODO 标记。
